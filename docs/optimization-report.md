# 番茄时钟项目优化分析报告（V1）

## 1. 项目现状评估

当前项目已经具备可发布的 MVP 能力，核心链路完整：
1. 计时器状态机可用（开始/暂停/继续/重置）。
2. 每日统计与任务联动可用。
3. 阶段4基础测试已覆盖关键逻辑。
4. UI 已完成主题化重构，整体可读性明显提升。

总体结论：适合进入“稳定性深化 + 体验精修 + 数据能力增强”的下一阶段。

## 2. 主要优化方向（按优先级）

### P0：数据可靠性与一致性（最优先）
1. JSON 持久化升级  
当前 `data/*.json` 适合单人单进程，后续建议迁移到 SQLite（事务、并发安全、查询能力更强）。
2. 写入原子化  
即便暂不迁移 SQLite，也建议先做“临时文件写入 + 原子替换”，降低数据损坏概率。
3. 数据版本字段  
给任务/会话记录增加 `schema_version`，方便后续字段演进和兼容迁移。

### P1：测试体系增强
1. 增加集成测试  
目前多是逻辑单测，建议补“计时归零 -> 统计写入 -> 任务累计”的端到端测试。
2. 异常路径测试  
重点覆盖文件占用、JSON 损坏、空数据迁移、非法状态值。
3. UI 关键流程回归脚本  
至少覆盖：新增任务、选择任务、完成番茄、删除任务确认。

### P1：用户体验精修
1. 计时状态文案与交互统一  
把内部状态值和用户文案彻底隔离，避免出现 `idle/running` 这类技术词泄露。
2. 任务行信息密度优化  
长标题截断与 hover 完整显示，移动端按钮布局再优化一轮。
3. 反馈节奏优化  
成功提示可做短时自动消失，避免提示堆叠。

### P2：产品能力扩展
1. 番茄模式扩展  
专注/短休息/长休息三段式，支持循环。
2. 可配置默认时长  
专注时长、休息时长、每日目标番茄数都可配置。
3. 历史趋势页  
按日/周展示番茄数和专注时长趋势，增强复盘价值。

## 3. 关键风险与应对

1. 风险：本地 JSON 在并发或异常退出时的数据一致性不足。  
应对：短期原子写入，中期迁移 SQLite。
2. 风险：功能增加后状态复杂度上升，容易出现重复计数。  
应对：继续坚持“归零单次事件”机制，并加端到端回归测试。
3. 风险：UI 改动频繁导致样式碎片化。  
应对：抽离统一 design tokens 和组件样式规范。

## 4. 建议的后续里程碑（4周示例）

1. 第1周：数据层增强  
完成 JSON 原子写入或 SQLite 迁移方案落地。
2. 第2周：测试补强  
补端到端用例和异常路径测试，接入基础 CI。
3. 第3周：体验精修  
统一状态文案、移动端适配、提示交互优化。
4. 第4周：功能升级  
加入短休息/长休息模式与历史趋势页雏形。

## 5. 结论

这个项目已经跨过“能跑”的阶段，下一步最有价值的是先补“可靠性和测试”，再扩功能。这样可以保证后续迭代速度更快、返工更少，也更像一个可持续演进的产品。
